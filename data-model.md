# Gigg: data model (draft)

Postgres. Every band-owned table has `band_id`. IDs are UUIDs; URLs use slugs.

## Conventions

- `archived_at timestamptz` on every user-facing entity. "Delete" in the UI = set `archived_at`. Restore = clear it.
- Child rows (set items, block songs, event contacts) are plain rows: they're replaced on edit, and the audit trail keeps the history.
- Slugs are unique per band per type, **including archived rows**, so restoring never collides.
- Auth tables are generated by Better Auth (passkey + magic-link plugins).

## Schema

Source of truth: [`src/server/db/schema.ts`](src/server/db/schema.ts) (app tables) and
[`auth-schema.ts`](src/server/db/auth-schema.ts) (generated by Better Auth: `users`, `sessions`,
`accounts`, `verifications`, `passkeys`).

Tables: `bands`, `memberships`, `slug_redirects`, `songs`, `venues`, `contacts`, `events`,
`event_contacts`, `setlists`, `sets`, `set_items`, `blocks`, `block_songs`, `files`, `feedback`,
`availability_requests`, `availability_responses`, `calendar_feeds`, `changes`.

Decisions made while building:
- **Child tables have `band_id` too** (`sets`, `set_items`, `event_contacts`, `block_songs`), so every audit entry has a band and every query can filter on band.
- `slug_redirects` has its own `id`; uniqueness is `(band_id, type, old_slug)` with nulls not distinct (band slugs have no band).
- **Availability**: an event has at most one *open* `availability_requests` row (partial unique index); it stores the date asked, so a moved event shows as stale. `availability_responses` has one row per person asked (`answer` null = waiting) and a `token_hash` for the emailed link. Only the hash is stored; answering by link sets the audit user to the responder. Requests are closed, never deleted.
- **Event times**: `start_time` / `end_time` are optional `time` columns (wall clock in the band's time zone). An end before the start means the next day; no end = 3 hours in the calendar feed. No times = an all-day event.
- **Calendar feed**: `calendar_feeds` holds one random token per person per band (stored as is, so settings can show the link again; reset replaces it). `/api/calendar/<token>.ics` serves option, confirmed and played events from a year ago on, as UTC times. Leaving the band (archived membership) makes the token return 404. Not audited: history would show the token.
- `users` comes from Better Auth; anonymisation (`anonymised_at`) is added when member removal is built.

## Hidden settings

Settings that exist in the database but have no UI yet. Change them with SQL.

| Setting | Column | Default | Used for |
|---------|--------|---------|----------|
| Time zone | `bands.time_zone` (IANA name) | `Europe/Amsterdam` | Event start/end times, the calendar feed |

Example: `update bands set time_zone = 'Europe/London' where slug = 'my-band';`

## Audit trail: a Postgres trigger

One generic trigger function on every table (except auth internals) writes to `changes`. See `drizzle/0002_audit.sql`. The app sets the user per transaction:

```sql
select set_config('app.user_id', $1, true);  -- true = transaction-local
```

Each row also gets `tx_id` (`txid_current()`), so one save's rows (a setlist save writes dozens) are shown together, with a before → after per field.

Why a trigger and not app code: it can't be bypassed (migrations, scripts and manual fixes are logged too), and it's one function instead of a rule every developer has to remember. Archive/restore shows up as an `update` where `archived_at` changes.

## Search

One `UNION ALL` query over songs, events (+ venue name), venues and contacts: `ILIKE` for substrings plus `pg_trgm` `<%` / `word_similarity()` for typos, ranked by score. GIN trigram indexes exist on the main name columns; the combined fields (e.g. contact name + email) are scanned, which is fine at band scale.

## Offline

Read operations go over GET in a read-only transaction; a service worker caches GETs network-first (see idea.md). Files will be cached on open.

## Dev mode

PGlite (Postgres in WASM) supports triggers and `pg_trgm`, so dev mode runs on a local file with no Docker and no cloud database. A seed script fills it with a fake band.
